# 공휴일·기상청 API 확인 결과

## 최종 운영 검증: 정상

2026-11-08 Vercel 운영 서버에서 공휴일 조회가 HTTP 200 / resultCode=00으로 성공했습니다. 전체 항목 수와 날짜를 검증한 파서가 2026년 공휴일 22개를 확인했고, 학년도 범위의 18개를 미리보기에서 표시했습니다. 기상청 단기·중기 육상·중기 기온예보도 모두 00 / NORMAL_SERVICE로 실제 데이터를 받아 화면에 표시했습니다.

동일한 공휴일 연 조회 URL·파라미터를 개발 환경에서 다시 호출하면 여전히 HTTP 400 / 코드 10이 반환됩니다. 실행 환경·요청 경로에 따라 결과가 다름을 확인했으며, 정확한 네트워크 계층의 원인은 확정하지 않았습니다. 인증키를 바꾸지 않고 운영 서버 호출로 정상 연동했습니다. 아래 오류는 개발 환경 진단 이력이며 현재 운영 연동 실패를 뜻하지 않습니다.

## 개발 환경의 원본 오류 기록

2026-11-08. 인증키는 서버 환경변수에서 읽고 URLSearchParams로 한 번 인코딩했습니다. 인증키 값은 아래 자료에서 제거했습니다.

공휴일의 실제 요청(월 조회, \_type 제외):

```
https://apis.data.go.kr/B090041/openapi/service/SpcdeInfoService/getRestDeInfo?ServiceKey=[REDACTED]&pageNo=1&numOfRows=100&solYear=2026&solMonth=05
```

HTTP 400. API resultCode/resultMsg 필드는 반환되지 않았으며, 게이트웨이 returnReasonCode는 10입니다. 원본 오류 응답:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<OpenAPI_ServiceResponse>
<cmmMsgHeader>
  <errMsg>INVALID_REQUEST_PARAMETER_ERROR</errMsg>
  <returnAuthMsg>잘못된 요청 파라미터 에러</returnAuthMsg>
  <returnReasonCode>10</returnReasonCode>
</cmmMsgHeader>
</OpenAPI_ServiceResponse>
```

연 조회와 ServiceKey/serviceKey 요청, 두 자리 월, JSON/XML 모두 같은 코드가 재현되었습니다. 날짜·교시 계산 엔진과 독립적으로 실패를 표시하며 resultCode=00, XML 유효성, 전체 항목 수·날짜·공휴일 항목 파싱을 모두 통과해야 초안에 반영합니다. 수동 수정한 날짜는 적용 후에도 보존됩니다. 연도 조회는 numOfRows=100으로 전체 자료를 요청하며, 한 번의 버튼으로 두 연도를 병렬 조회하고 해당 학년도 3월~다음 2월만 반영합니다. 어느 한 조회라도 실패하면 계획을 변경하지 않습니다.

개발 환경에서는 기상청 단기예보 및 중기 육상예보도 동일 키로 HTTP 400 / 코드 10을 반환했습니다. 두 서비스가 같은 키인 것은 공공데이터포털의 공통 인증키 방식과 양립합니다. 다만 각 서비스의 활용 신청·승인·키 적용 상태는 별도 확인이 필요하며, 이 오류만으로 인증키가 잘못됐다고 단정할 수 없습니다. 운영 화면에서는 실제 예보가 표시됩니다. 조회 실패 시 오류를 표시하며 예보를 생성하지 않습니다.

단기예보는 학교의 격자 X/Y, 중기예보는 육상·기온 구역 코드를 사용합니다. 기본 위치는 서울이며 화면에서 학교 위치로 변경할 수 있습니다. 날씨는 가까운 야외활동 준비와 다음 주 행사 검토를 위한 참고로 제공하고 연간 기본안을 자동 수정하지 않습니다.

## 학년도 전체 불러오기 운영 검증

`f2ff21e` 배포의 버튼 한 번으로 2026학년도 공휴일 23일(2026년 3~12월 18일, 2027년 1~2월 5일)을 가져왔습니다. 정상 코드·완전 파싱 검사를 통과한 두 해의 결과가 반영되었습니다. 연간 저장·새로고침 후 JSON 백업과 별도 SQL 조회에서 같은 23일을 확인했습니다. 3월 2일의 수동 요일 교체, 1월 1~5일 방학 구간, 학교업무 항목도 보존됐습니다.

브라우저 보조 도구의 원본 응답 캡처는 응답 본문 수명/요청 전송 제약으로 실패했습니다. 이 캡처 실패를 API 실패로 해석하지 않으며 성공 응답 원문을 저장했다고 주장하지 않습니다. 실제 기능 검증은 화면 반영·DB 저장·새로고침·JSON 내보내기 및 DB 독립 조회를 근거로 합니다.
